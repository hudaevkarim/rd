# rd — совместное чтение книг и аудиокниг в приватных комнатах

Децентрализованное P2P-приложение. Книги, комментарии и прогресс живут только на
устройствах участников; signaling-сервер помогает соединиться и не видит
содержимого комнаты.

```
┌──────────┐   WSS (SDP/ICE)   ┌──────────────┐   WSS (SDP/ICE)   ┌──────────┐
│  Аня     │ ────────────────► │  signaling   │ ◄──────────────── │  Борис   │
│ браузер  │ ◄──────────────── │  (stateless) │ ─────────────────► │ браузер  │
└────┬─────┘                    └──────────────┘                    └────┬─────┘
     │                                                                   │
     │        Data Channel: AES-GCM, заголовок кадра = AAD               │
     └─────────────────────── E2EE, напрямую ────────────────────────────┘
                                    │
                       ┌────────────┴────────────┐
                       │   Yjs: комментарии,      │
                       │   каталог, присутствие    │
                       │   файлы — чанками по 16 КБ│
                       └────────────────────────────┘
```

## Что реализовано

| Область | Состояние |
|---|---|
| Комнаты: создание, вход по id + фразе, список участников, статусы | готово |
| E2EE: PBKDF2 → ECDH P-256 + Ed25519 → HKDF → AES-GCM с окном переигрывания | готово |
| Код безопасности (защита от подмены ключей посредником) | готово |
| P2P: mesh, perfect negotiation, два канала (управление / файлы) | готово |
| Топология для больших комнат: выбор relay, перевыборы, mesh ↔ star | выбор и соединения готовы, **пересылка трафика — нет** (см. «Топология комнаты: mesh и relay») |
| CRDT: комментарии (треды, реакции), каталог книг, присутствие | готово |
| Передача файлов: чанки 16 КБ, SHA-256, скользящее окно 256 КБ, backpressure по `bufferedAmount` и по ACK, докачка с обрыва | готово |
| EPUB: разбор, оглавление (EPUB 3 и NCX), рендер без `innerHTML` | готово |
| FB2: разбор, кодировки (UTF-8/windows-1251/koi8-r), оглавление из `<section>`, рендер без `innerHTML` | готово |
| Якоря комментариев: цитата + контекст, устойчивость к переразметке | готово |
| Спойлеры: маскирование до места комментария | готово |
| Офлайн-режим: состояние комнаты в IndexedDB | готово |
| Аудиокниги: MP3/M4B, плеер, комментарии по времени, мягкая синхронизация позиции | готово |

Что осознанно не входит: аккаунты, серверная модерация, любые данные на сервере,
телеметрия. Код под MIT (см. «Лицензия»).

## Запуск

Нужен Node.js ≥ 20.11 (в тестах использовался 22.23) и браузер с WebRTC
(Chrome 137+, Firefox 130+, Safari 17+). WebRTC требует HTTPS или `localhost`.

```bash
npm install
cp .env.example .env          # необязательно, умолчания рабочие

npm run dev:server            # signaling на :8787
npm run dev                   # клиент на :5173
```

Продакшен-сборка:

```bash
npm run build                 # signaling (esbuild) + клиент (vite)
npm run start:server
```

Откройте приложение в двух вкладках, создайте комнату в первой, скопируйте
идентификатор во вторую, введите одну и ту же парольную фразу.

## Проверки

```bash
npm run typecheck             # tsc --noEmit по всему монорепо
npm test                      # 413 юнит-тестов (vitest)
npm run test:coverage

npm run test:e2e:install      # один раз: скачать браузер Playwright
npm run test:e2e              # 24 сквозных UI-теста
npm run test:e2e:headed       # то же с видимым браузером
npm run test:e2e:ui           # интерактивный режим Playwright
```

Покрытие — около 88 % строк. Основная масса тестов — не юнит-тесты, а сквозные:
две ноды проходят весь путь (подключение → E2EE-рукопожатие → синхронизация Yjs →
передача файла → докачка после обрыва) на in-memory реализации WebRTC. Ошибки
на стыках слоёв — несовпадение направлений ключей, потерянный заголовок кадра,
зацикливание broadcast, гонки в обработке чанков — не видны в юнит-тестах по
отдельности, и именно их ловит этот тест.

Интерфейс покрыт частично: `packages/web/tests/{reader-render,comments-panel,audio-position}.test.tsx`
и `packages/library/tests/fb2-render.test.tsx` поднимают настоящий DOM (jsdom) и
рендерят настоящие компоненты. Это дороже остальных тестов, но без DOM не
проверить вещи, которые ломаются только в браузере: например, что хост главы есть
в DOM на любой стадии (от этого зависел баг с пустой страницей при смене книги),
что панель комментариев переключается вместе с открытой книгой, или что `<script>`
из FB2 не выполняется.

### Сквозные UI-тесты (Playwright)

Отдельный пакет `@rd/e2e`. Playwright сам поднимает signaling и Vite через
`webServer` и гасит их после прогона, поэтому ни запускать серверы руками, ни
писать `globalSetup`/`globalTeardown` не нужно. Порты свои (8790 и 5199), чтобы
тесты не зависели от того, запущено ли что-то у разработчиста, и не ломали его
работающий сервер.

| Файл | Что проверяет |
|---|---|
| `room.spec.ts` | комната, второй участник по идентификатору, поимённое присутствие, P2P-соединение, отказ при чужой фразе |
| `books.spec.ts` | импорт EPUB и FB2, отсутствие файла до запроса, передача по запросу, рендер у обоих, оглавление, вложенный раздел FB2 |
| `comments.spec.ts` | якорь по фрагменту и его разрешение у соседа, реакции, изоляция по книге, таймкод и перемотка по клику |
| `audio.spec.ts` | длительность, play/pause, перемотка, отсутствие отката, мягкая синхронизация и её выключенность по умолчанию, присутствие по книгам |
| `ice.spec.ts` | клиент запрашивает `/config` при входе, ответ разбирается, CORS-заголовок есть, вход работает и при недоступной конфигурации |

Три неочевидых решения, каждое из которых уже стоило времени:

1. **`--disable-features=WebRtcHideLocalIpsWithMdns`.** По умолчанию Chromium прячет
   локальные адреса за именами `a1b2c3d4-….local`. Внутри одной машины это
   работает, но mDNS-резолвинг зависит от сетевого стека, и на разных образцах CI
   срабатывает по-разному. С флагом кандидат содержит настоящий адрес, и пересылка
   через signaling одинакова везде.
2. **`--host 127.0.0.1` у Vite.** Без него Vite слушает только `localhost`, который
   на Windows резолвится в `::1`, а проверка готовности ходит на `127.0.0.1` и
   получает отказ при живом сервере. Падение выглядит как «сервер не поднялся»,
   хотя он поднят.
3. **Файлы книг собираются в коде** (`tests/fixtures/files.ts`). EPUB — настоящий zip
   на fflate, FB2 — настоящий windows-1251 без BOM, аудио — WAV нужной длины.
   Двоичные файлы в репозитории нечитаемы, и WAV не тянет за собой кодек.

Выделение текста в тестах строится прямо по строке, а не двойным кликом: двойной
клик выделяет слово, границы которого зависят от шрифта и разбиения строк, и на
другой машине выделилось бы другое слово.

**Звук в headless Chromium не слышен, но декодируется.** Проверяются всё, кроме
самого звука: `currentTime` растёт, play/pause переключается, длительность
известна. Сам звук проверяется на машине разработчика.

`packages/e2e/webrtc-smoke.mjs` — отдельная проверка окружения (не тест
приложения): поднимает два `RTCPeerConnection` в одной странице и печатает
состояние ICE и обмен по DataChannel. Именно она установила, что WebRTC в
headless Chromium работает.

## Нагрузочное тестирование signaling

```bash
npm run test:load             # ступени 50 → 100 → 200 → 500
npm run test:load:ratelimit   # проверка отказа при превышении лимита
npm run test:load:deep        # добавляет 1000 и 2000 — поиск предела
npm run test:load:leak        # четыре цикла, проверка роста памяти
```

Нужен [k6](https://grafana.com/docs/k6/latest/set-up/install-k6/). Бинарник ищется
в `PATH`, в `K6_BIN` и в стандартных каталогах установки. Отчёты и сырые выгрузки
k6 складываются в `reports/` (в git не попадают).

Обёртка сама поднимает signaling на свободном порту, прогревает его, снимает CPU и
RSS процесса вместе с `/healthz`, гасит сервер и пишет сводку в JSON.

### Почему k6, а не Artillery

Artillery написан на Node и крутится в том же цикле событий, что и сервер под
нагрузкой. На VPS с 1 vCPU это делает измерение бессмысленным: генератор отнимает
у сервера его единственное ядро, и в результат попадает не поведение сервера, а
борьба Node с Node. k6 — отдельный бинарник на Go, своей памятью и планировщиком,
плюс встроенные метрики для WebSocket.

### Сценарий говорит на настоящем протоколе

`join` с настоящим descriptor'ом, `signal` и `candidate` с настоящими по форме
SDP и ICE, `ping` для замера задержки. Нагрузка на «сервер, который просто держит
сокеты» измеряла бы сокеты, а не разбор сообщений, проверку лимитов и рассылку
по комнате.

План ступеней передаётся в k6 одной строкой и используется обёрткой для разбивки
результатов по ступеням, поэтому цифры в таблице и фактический прогон не могут
разойтись.

### Измеренные числа

Windows, 12 ядер, 16 ГБ, Node 22, **сервер и генератор на одной машине**.

| Одновременных соединений | CPU (среднее) | CPU (пик) | RSS | p50 / p95 / p99 подключения |
|---|---|---|---|---|
| 50 | 4,5 % | 8,4 % | 61 МБ | 1 / 2 / 3 мс |
| 100 | 5,1 % | 10,8 % | 68 МБ | 1 / 2 / 4 мс |
| 200 | 13,7 % | 21,1 % | 81 МБ | 1 / 3 / 6 мс |
| 500 | 18,0 % | 30,3 % | 101 МБ | 1 / 8 / 12 мс |
| 1000 | 51,5 % | 121 % | 105 МБ | — / 222 / 317 мс |
| 2000 | предел среды | 116 % | 133 МБ | — / 576 / 969 мс |

Задержка ответа сервера (`ping` → `pong`) на 500 соединениях: p50 0 мс, p95 2 мс,
p99 6 мс. При 5817 подключениях — ни одного отказа, ни одного неожиданного ответа
сервера, 16 344 успешно пересланных сигнала.

**До 500 соединений сервер не напрягается:** 18 % одного ядра, 100 МБ RSS,
подключение за единицы миллисекунд. На 1000 соединениях появляются первые
признаки деградации — рост `p95` подключения до 222 мс и пропуски опросов
`/healthz`. На 2000 соединениях картина такая же, но гораздо глубже.

### Где предел на самом деле — и почему это не сервер

На этой машине прел на **установлении соединений**, а не на их обслуживании, и
проверено это было так:

- при 2000 **полностью молчащих** соединениях (ни одного байта трафика) отказы
  те же самые: `ws_connecting` p50 390 мс, 38 тысяч неудачных подключений;
- процесс сервера при этом занимал **1,2 ядра из 12**, то есть упирался не в CPU;
- пиковое число соединений, до которого сервер доходил, — 2020.

То есть генератор и сервер на одной машине делят сетевой стек ОС, и на Windows
установление тысяч loopback-сокетов становится раньше, чем сервер перестаёт
справляться. **Объявлять 1000–2000 соединений пределом сервера на основании этих
цифр нельзя.** Пункт 1 ниже — единственное, что здесь измерено честно.

По той же причине эти числа — верхняя граница для сервера и нижняя для
генератора. Для VPS нужен отдельный генератор; команды ниже.

### Проверка на утечки

Четыре одинаковых цикла по 500 соединений, между ними пауза 15 с:

| Цикл | Пик RSS | RSS после |
|---|---|---|
| 1 | 100,2 МБ | 99,4 МБ |
| 2 | 104,9 МБ | 59,5 МБ |
| 3 | 100,7 МБ | 76,2 МБ |
| 4 | 102,0 МБ | 99,8 МБ |

**Утечки нет.** Критерий — рост ПИКА (1,8 МБ за четыре цикла, то есть шум), а не
состояния покоя.

Критерий выбран именно так, потому что оба наивных варианта ошибаются: «RSS
вернулся к исходному ±10 %» показывает утечку на любом Node, потому что V8 не
отдаёт кучу ОС сразу; а «RSS растёт от цикла к циклу» — наоборот, ловит невыполненный
сбор мусора. Растущее состояние покоя при неизменных пиках означает, что рабочее
множество не выросло: память не забыта, а просто не отдана.

### Что изменено по итогам

1. **Отключено логирование каждого запроса** (`disableRequestLogging`). На
   продуктовом `LOG_LEVEL=info` Fastify писал по строке на каждое рукопожатие:
   измерение — 6060 строк на 5818 подключений, вместе с адресом участника. После
   правки — 6 строк на тот же прогон. Для приложения, которое обещает не хранить
   метаданные, попадание адресов участников в журнал ещё и противоречиво. Ошибки и
   нештатные завершения остаются видны: их пишет обработчик ошибок, а не журнал
   запросов.
2. **`LISTEN_BACKLOG` = 4096 вместо умолчания Node в 511.** Очередь входящих
   соединений при всплеске переполнялась, и новые соединения получали отказ вместо
   ожидания. Честно: на измеренных цифрах это **не изменило результат** — прел
   оказался в другом месте. Изменение оставлено как разумное умолчание для VPS, но
   оно не проверено измерением.
3. **`MAX_BUFFERED_BYTES` и проверка `slow-consumer`** уже были на месте: клиент,
   не читающий данные, отключается. В прогонах не срабатывали.

### Настоящий предел: лимит подключений по IP

`CONNECT_PER_MIN` = 30 на адрес, и это ограничивает не сервер, а продукт.
За одним публичным IP (офис, мобильный оператор, общежитие) сидят десятки
участников, и каждому достанется 30 попыток в минуту — при переподключении после
обрыва связи комната станет недоступна.

Это же помешало измерению: с localhost все соединения приходят с 127.0.0.1, и при
продуктовых 30 в минуту нагрузка упёрлась бы в лимит на тридцатом соединении.
Обёртка поднимает лимит до потолка, который допускает сам сервер (10 000).

Разумное решение для продакшена — `CONNECT_PER_MIN` от 1000 и явная документированная
рекомендация, либо ограничение по адресу с возможностью доверенного исключения.
Сейчас это не сделано: цифра меняет поведение продукта, и решение за оператором.

### На VPS

Генератор и сервер должны быть на разных машинах, иначе повторится то же, что
описано выше.

```bash
# ─── На VPS (Ubuntu 22.04 / 24.04) ───
sudo apt-get update
sudo apt-get install -y nodejs npm git
sudo npm install -g n
sudo n 22
git clone <репозиторий> rd && cd rd
npm ci
npx playwright install --with-deps chromium   # нужен для e2e, не для нагрузки

npm run build:server
# Ограничить сервер одним ядром — иначе он получит все ядра VPS и сравнение
# с «1 vCPU» будет бессмысленным:
sudo apt-get install -y systemd-cpuset
# проще всего — через taskset на время прогона:
taskset -c 0 env PORT=8787 NODE_ENV=production \
  LOG_LEVEL=warn node packages/signaling/dist/main.js &
sleep 2 && curl -fsS http://127.0.0.1:8787/healthz

# Генератор — на ДРУГОЙ машине, с k6:
K6_BIN=/usr/local/bin/k6 node scripts/load-test.mjs \
  --stages 20:100,20:200,30:500,30:1000,20:0 --hold 20000
```

Полезно смотреть параллельно:

```bash
htop                       # CPU и память процесса
ss -tan | grep -c 8787     # число соединений
tail -f /var/log/syslog | grep node
```

Чего ждать на 1 vCPU / 1 ГБ: по измерениям на 12 ядрах сервер занимает ~18 % ядра
на 500 соединениях и ~0,5 ядра на 1000, то есть **одного vCPU хватает примерно на
1000–2000 соединений**, и память упирается раньше: около 100 МБ на 500 соединений,
то есть 1 ГБ хватает примерно на 4000–5000. Это оценка по линейной
экстраполяции, а не измерение: проверяется только на VPS с отдельным генератором.

## Ключевые инженерные решения

### Почему свой signaling, а не Trystero и не y-webrtc

`y-webrtc` ходит через публичные трекеры и не шифрует полезную нагрузку: там
комната защищена только именем, а весь CRDT-трафик виден оператору трекера.
Trystero устроен так же. Для приложения, где единственная ценность — приватность,
это неприемлемо, поэтому signaling и Yjs-провайдер написаны здесь: ~200 строк
поверх `y-protocols`, протокол совместим с любым другим Yjs-клиентом.

### Откуда берётся ключ пары

В KDF входят три независимых материала:

- **парольная фраза** — её знают только участники комнаты; сервер не может
  прочитать данные;
- **ECDH P-256** — приватный ключ есть только у пира; посредник, подменивший
  публичные ключи, не сможет установить рабочий канал даже со знанием фразы
  (соединение просто не расшифруется);
- **отсортированные identity-ключи** — чтобы направление ключей не зависело от
  того, кто подключился первым.

Каналы `ctrl` и `file` разведены по разным `info`, а каждое направление — по
своей роли: четыре независимых ключа AES на пару, поэтому счётчики nonce можно
начинать с нуля в каждом направлении и никогда не повторить пару «ключ + nonce».

P-256, а не X25519: WebCrypto в Node не знает кривую `X25519`, и без неё
криптографию нельзя покрыть тестами без браузера. Формат провода хранит байты
ключей, поэтому переход — смена одной константы.

### Почему заголовок кадра передаётся открытым

Заголовок нужен AEAD как additional data, а AAD задаётся **до** шифрования —
зашифровать его нельзя. Поэтому в заголовке лежит только тип кадра и, для чанка
файла, идентификатор передачи, смещение и длина. Всё содержимое — в
зашифрованном теле. Из-за этого в крипто-пакете намеренно **нет** метода
«зашифровать JSON в заголовок»: такая возможность один раз утекла бы весь чат
комнаты в открытом виде, и тест на это есть.

### Почему окно переигрывания сдвигается на `diff + 1`

Кадры уходят в канал в порядке **завершения шифрования**, а счётчики выдаются в
порядке вызовов: `crypto.subtle.encrypt` асинхронен, поэтому два управляющих кадра,
запущенные подряд, могут дойти до сети переставленными. Приёмник обязан это
пережить, для чего счётчик отслеживается скользящим окном в 64 позиции.

При сдвиге окна вперёд на `diff` только что принятый счётчик занимает позицию 0,
поэтому прежние биты сдвигаются на `diff + 1`, а не на `diff`. Со сдвигом на
`diff` окно помечало как уже принятый счётчик, который ещё не приходил, и
настоящий кадр отбрасывался как повтор:

```
... 46, 47, 49, 48   ← 48 отброшен как «повтор», которого не было
```

`PeerLink` считал это атакой и рвал соединение вместе с идущей передачей файла.
Разница в один кадр — самый частый случай: она возникает всякий раз, когда
шифруются два управляющих кадра одновременно, то есть на любой активности Yjs.
На это есть регрессия в `packages/crypto/tests/crypto.test.ts`.

### Почему кадры выходят из ссылки строго по очереди

DataChannel доставляет кадры упорядоченно, и весь протокол на этом стоит:
получатель файла принимает чанк только если `offset` совпал с ожидаемым, Yjs
различает обновления по порядку. Но `crypto.subtle.decrypt` асинхронен, поэтому
`void aead.open(frame).then(...)` отдаёт кадры наружу **в порядке завершения
расшифровки**, а не прихода.

Это стоило нам потерянных файлов: терялся ровно один чанк, дальше получатель
сдвигал `expectedNext` уже не туда, отбрасывал каждый следующий чанк как
«перепрыгнувший» и просил докачку с места, куда отправитель ещё не дошёл.
Воспроизводилось примерно в 10 % запусков на файле в 700 КБ.

Поэтому на каждый канал в `PeerLink` стоит `SerialQueue`
(`packages/p2p/src/serial-queue.ts`): расшифровка идёт подряд, а выдача
наружу — строго в порядке прихода. Ошибка внутри задачи не рвёт очередь, иначе
один битый кадр навсегда остановил бы приём.

Следом сразу нашлась вторая половина того же бага: задача отправителя удалялась,
как только все пиры **согласились принять** файл. Докачка после этого приходила
в `#sending.get(...)`, получала `undefined` и молча игнорировалась, а получатель
оставался ждать недостающий кусок — без ошибки и без конца. Теперь задача живёт
до `file-finish` от каждого, то есть до подтверждения, что файл получен целиком.

### Место чтения: своё для каждой книги

Открыли вторую книгу — место в первой потерялось, возвращаться приходилось
листать с начала. Для аудиокниг было хуже: там позиция вообще бралась из
заметки в каталоге комнаты, то есть из значения, **общего для всех
участников**: своё место там не выжить было в принципе, чужая перемотка его
обнуляла, а перезагрузку страницы оно не переживало. Плюс заметка хранила долю
0..1, а в `seek()` уходило это значение как секунды — восстановление прыгало на
первые полсекунды записи.

Теперь место хранится **по книге** (`state.positions`, ключ — id книги) и лежит в
IndexedDB, а не в CRDT-документе. Это осознанно: документ синхронизируется с
соседями, и личная история чтения в нём стала бы читаемой любым участником
комнаты. Присутствие и так рассказывает соседям, где я сейчас, но не где я был
за все прочитанные книги.

Два правила, которые стоит знать при правке этого кода:

- **Хост главы в `reader.tsx` монтируется всегда**, а не только в «успешной»
  ветке рендера. Эффект отрисовки главы работает с `hostRef.current`; если хоста
  в момент его срабатывания нет, эффект выходит, а `chapter` уже не меняется —
  и глава не отрисуется никогда. Нажатие «Следующая» маскировало это, меняя
  `chapter`.
- **`comments.tsx` фильтрует список по `bookId` сам.** Раньше фильтр стоял в
  сессии и смотрел на `state.position.bookId` — на книгу, которую читают сейчас,
  а не на открытую. Отсюда чужие комментарии и обновление списка только после
  правки в документе («надо что-то написать, чтобы подтянулись»).

### Якоря комментариев вместо CFI

Якорь — это (глава, блок, смещение) **плюс цитата с контекстом**. Он переживает
переразметку, переносы строк и другую разбивку на абзацы. Поиск идёт от
точных координат к цитате в блоке, затем в главе, затем по книге.

Инвариант, на котором всё держится: дерево блока нормализуется **на этапе
разбора**, поэтому `text(дерево) === block.text`, а смещения в DOM равны
координатам якоря. Без этого комментарии привязывались бы к произвольным местам.

### Контрольная сумма файла

`root = SHA-256( SHA-256(чанк₀) ‖ … ‖ SHA-256(чанкₙ) )`. Хеши считаются
потоково, файл не держится в памяти целиком. Хеши чанков сохраняются рядом с
данными, поэтому после обрыва связи общая сумма собирается заново, а файл не
качается с нуля.

### Никакого `innerHTML`

Содержимое книги недоверенное — и EPUB, и FB2. DOM строится через
`createElement`/`textContent` из разобранного дерева с закрытым белым списком
тегов; атрибуты вида `onclick` и `style` не копируются вообще, текст книги всегда
остаётся текстом. Санитайзер не нужен, потому что нет пути для выполнения кода.

Белый список **атрибутов** тоже закрытый: в дерево блока попадают только `href`
у ссылок и `alt`/`title` у картинок. Это важно именно как белый список, а не как
«убрать опасное»: при блоклисте прошли бы `onload`, `formaction`, `srcset` и всё,
что придумают в следующей версии HTML. Схему ссылки проверяет `safeHref` при
рендере, поэтому `javascript:` из книги остаётся текстом и ссылкой не
превращается.

## FB2

FB2 разбирается в ту же структуру «главы → блоки», что и EPUB. Отдельный тип для
него не заводился намеренно: рендерер, якоря комментариев, прогресс, спойлеры и
передача файла работают со структурой и не знают о формате. Без FB2 не пришлось бы
ни одной ветки «а если формат fb2» ни в одном из этих мест.

Что пришлось учесть отдельно от EPUB:

- **`<title>` — это заголовок главы**, а не `<title>` из `<head>`. Пропуск его по
  правилам EPUB выкинул бы все заголовки книги. Список пропускаемых тегов стал
  параметром разбора блоков.
- **Вложенные `<section>` остаются частью главы.** Если дробить книгу на каждый
  раздел, в главе первой получаются «главы» по одному абзацу, и оглавление
  становится бессмысленным. Вложенный заголовок помечается как подзаголовок.
- **`<empty-line/>`** разделяет абзацы, но не даёт отдельного блока (см.
  ограничения ниже).
- **`<binary>`** (Base64-иллюстрации внутри того же файла) вырезается до разбора:
  иначе килобайты Base64 попадали бы в текст книги и в поиск цитат.
- **Акцидентные теги FB2** (`<emphasis>`, `<strikethrough>`, `<cite>`) добавлены
  в белый список инлайна: без них курсив и зачёркивание терялись бы при разборе.

### Кодировки

Порядок источников, от более надёжного к менее:

1. **BOM** — однозначный признак, побеждает всегда.
2. **Объявление `<?xml encoding="..."?>`** — но только если байты при этом не
   образуют корректный UTF-8. В однобайтовой кодировке строгая проверка
   бесполезна (там «валидно» абсолютно всё), а в объявлении врут часто: файлы
   «в windows-1251» с настоящим UTF-8 внутри встречаются регулярно.
3. **Строгая проверка UTF-8** (`fatal`, а не «заменить битые на �»). Настоящий
   однобайтовый русский текст почти никогда её не проходит: в windows-1251 и
   koi8-r все байты `0xC0..0xFF`, а в UTF-8 `0xC0/0xC1` запрещены, а
   `0xC2..0xDF` обязаны сопровождаться байтом продолжения из `0x80..0xBF`,
   которого в этих кодировках практически нет.
4. **Распределение байтов** — когда осталось выбрать между однобайтовыми. Это
   единственный шаг, который опирается на устройство кодировок, а не на догадки
   о правдоподобии текста: в `windows-1251` строчные русские буквы лежат в
   `0xE0..0xFF`, в `koi8-r` — в `0xC0..0xDF`, а в русской прозе строчных букв
   подавляющее большинство. На тестовых данных разделение абсолютное (0.95 против
   0.04).

Первый вариант этой схемы считал «правдоподобие» готового текста — кириллица,
пробелы, пунктуация — и это **не работало вовсе**: количество кириллицы и пробелов
у обеих расшифровок одинаковое, потому что обе кодировки отображают ASCII-пробел
в `0x20`, а кириллицу — в тот же диапазон. Оценка всегда выходила равной, и выбор
шёл по порядку проб, то есть по подбрасыванию монетки. Это зафиксировано
тестом `выбирает однобайтовую кодировку по распределению байтов`: он падает, если
вернуть выбор «по порядку».

Честное ограничение: без BOM и без объявления однобайтовые кодировки различаются
только таким способом. Для книги, где русского текста почти нет, разницы не
будет — там результаты практически совпадают.

### Невалидная разметка

FB2 в дикой природе часто не является корректным XML. Разбор настроен на
терпимость, но не на доверчивость:

- вырезаются инструкции `<?…?>`, CDATA, `<!DOCTYPE …>` с внутренним подмножеством
  и незакрытые комментарии;
- `processEntities` выключен, внешние сущности не читаются — это отсекает
  billion laughs и XXE;
- **незакрытый `<!--` убирается только до конца строки**, а не «до конца файла».
  Схлопывание в конец файла уносило с собой `<body>`, все `<section>` и весь
  текст: потеря всей книги из-за одной забытой пары дефисов.

### Выбор формата при открытии

Формат определяется по содержимому файла, а не по расширению и не по типу от
браузера: у FB2 корневой тег `FictionBook`, у EPUB — zip-сигнатура. Подсказка из
каталога комнаты учитывается, но не решает — каталог приезжает по общей CRDT и
является недоверенными данными. Иначе книга, переименованная отправителем при
передаче, не открывалась бы у получателя.

## STUN и TURN

### Откуда клиент берёт ICE-конфигурацию

Цепочка ровно одна, и важно, что она не разорвана:

```
ICE_SERVERS (на сервере)  →  GET /config  →  RTCPeerConnection({ iceServers })
                                    ↓ если недоступно или пусто
                      VITE_ICE_FALLBACK (в сборке клиента)
```

Клиент запрашивает `/config` при входе в комнату и передаёт ответ в `RoomMesh`.
Ответ проверяется поштучно: элементы без строкового `urls` отбрасываются, остальные
применяются. Это не перестраховка — `new RTCPeerConnection({ iceServers })`
**бросает исключение** на некорректной конфигурации, то есть один плохой элемент
в ответе роняет вход в комнату целиком.

Если сервер недоступен, ответил ошибкой или вернул пустой список, клиент берёт
`VITE_ICE_FALLBACK` и **входит в комнату в любом случае**. Вход не блокируется
дольше трёх секунд: лучше войти без STUN, чем не войти.

В журнале браузера появляется строка `[rd/ice]` — только когда сервер не дал
конфигурацию. Если её нет, применён список сервера и всё штатно.

Адрес `/config` выводится из `VITE_SIGNALING_URL` заменой `ws`→`http` и хвоста
`/ws`→`/config`, с сохранением префикса пути: сервер не обязательно стоит в корне
домена.

### Свой STUN

Достаточно одной переменной на signaling-сервере:

```bash
ICE_SERVERS=stun:stun.example.com:3478
# несколько — через запятую:
ICE_SERVERS=stun:stun1.example.com:3478,stun:stun2.example.com:3478
```

Публичный STUN Cloudflare стоит в значении по умолчанию. Он не видит ни
содержимого комнаты, ни ключей — только ваш внешний адрес и факт соединения.

### Свой TURN (coturn)

TURN нужен там, где STUN не справляется: два симметричных NAT (часто мобильный
интернет и корпоративный VPN) или заблокированный UDP.

```bash
# /etc/coturn/turnserver.conf
listening-port=3478
tls-listening-port=5349
fingerprint
lt-cred-mech
user=rd:пароль_подлиннее
realm=example.com
```

Затем на signaling-сервере — JSON-формой, потому что нужны учётные данные:

```bash
ICE_SERVERS=[{"urls":"turn:turn.example.com:3478?transport=udp","username":"rd","credential":"пароль_подлиннее"}]
ICE_SERVERS=[{"urls":["turn:turn.example.com:3478","turns:turn.example.com:5349"],"username":"rd","credential":"пароль"}]
```

**TURN видит шифротекст и метаданные** — адреса, тайминги, объём переданного.
Он не может расшифровать комнату, но видит, кто с кем и сколько общается.
Поэтому TURN здесь никогда не включается по умолчанию: это явное решение
оператора, и для приложения, построенного вокруг приватности, включать его —
значит признать, что часть метаданных теперь у третьей стороны.

TURN-серверу нужен публичный адрес и UDP/TCP, поэтому в контейнере это означает
`network_mode: host` либо проброс портов 3478 и 5349.

### Проверить вживую

В журнале браузера при входе в комнату:

- нет строки `[rd/ice]` — применён список signaling-сервера;
- «работаем на резервном списке» или «на локальных кандидатах» — сервер не дал
  конфигурацию, и это стоит проверить (частая причина — `CORS_ORIGIN`).

Самый надёжный признак того, что ICE работает, — соединение между двумя разными
сетями. Сквозные тесты этого не проверяют: они гоняют две вкладки на одной машине.

## Передача файлов

Маршрут: `importBook` → копия в IndexedDB + запись в общем каталоге → кнопка
«передать участникам» → `file-offer` по ctrl-каналу → `file-accept` → чанки по
`rd-file` → сборка в Blob → проверка контрольной суммы.

Три неочевидных правила, каждое из которых однажды ломало передачу:

1. **Наличие файла определяется по хранилищу, а не по кэшу разбора.** Разбор есть
   только у EPUB; аудиокнига лежит как есть. Проверка по кэшу показывала
   «файла нет» для только что загруженного mp3.
2. **Имя файла при передаче обрезается до лимита протокола** (200 символов).
   Имя с диска ничем не ограничено, а превышение отбрасывало всё предложение
   вместе с ним — снаружи это выглядело как «передал, а файл не пришёл», потому
   что каталог книги ехал по CRDT независимо.
3. **Файл принимается только при наличии записи в каталоге комнаты.** Иначе
   любой участник завалил бы диск файлами без спроса. Отказ виден пользователю:
   «файл отклонён: нет в каталоге».

Подробный журнал (номер чанка, `bufferedAmount`, паузы, таймауты) идёт в
`onTrace` и в браузере пишется в консоль под префиксом `[rd/передача]` — по нему
видно, на каком чанке передача встала.

Проверено тестами на mock-канале с настоящей очередью: рост `bufferedAmount`,
событие по спеке WebRTC, замедленный приёмник и сеть, переставшая забирать
данные без закрытия канала; плюс сквозные тесты настоящей сессии на двух
участниках (аудио, EPUB, длинное имя, отказ без записи в каталоге, две книги
подряд, порядок чанков).

## Топология комнаты: mesh и relay

Полная mesh даёт `n·(n−1)/2` соединений: на 8 участниках это 28 соединений и
56 DataChannel, на 20 — уже 190 и 380. Дальше это не растёт ни по числу
соединений, ни по трафику: каждая книга едет по своему пути, и объём
получается квадратичным.

Поэтому есть вторая топология — star через **relay**: один участник соединён со
всеми, остальные — только с ним. Соединений `n−1`.

### Как выбирается relay

Правило намеренно вынесено в чистую функцию `decideRelay` — это ровно та логика,
которую должны повторять за нас все участники:

1. **Relay — минимальный идентификатор среди доступных участников.** Все считают
   одно и то же из одного и того же списка, поэтому координатор не нужен: он и
   был бы единственной точкой отказа.
2. **Список участников одинаковый у всех** — он приходит через signaling при
   входе и дополняется сообщениями о приходе и уходе.
3. **Перевыборы автоматические.** Relay вышел — он исчез из списка, следующий
   минимум становится relay'ем. Ничего рассылать не нужно.
4. **Ручной выбор побеждает автоматический** (минимальный из названных, если
   ручные выборы разные). Нужен для случая «автоматически выбрали мобильное
   устройство с плохой связью».
5. **Перегруженный relay исключается из выборов** — он сам объявляет высокую
   нагрузку, остальные перестают его предлагать.

### Что реализовано, а что нет

| Что | Состояние |
| --- | --- |
| Выбор relay, одинаковый у всех участников | ✅ есть, покрыто тестами |
| Перевыборы при уходе relay | ✅ есть |
| Ручной выбор relay | ✅ есть (`RoomRelay.preferRelay`) |
| Исключение перегруженного из выборов | ✅ есть |
| Переключение mesh ↔ star, порог и соединения | ✅ есть, включая соединения после перевыборов |
| Ключ для отправки произвольному участнику | ✅ есть, ключевой домен отдельный |
| **Пересылка трафика через relay** | ❌ **нет** |

**Пересылка не реализована**, поэтому star-топология **выключена по умолчанию**
(`RoomMeshOptions.relay` — не `true`, а `false`). Это не формальность: в star
лист соединён только с relay, и без пересылки сообщения от других листьев он
просто не получит. При этом в списке участников такой лист выглядит обычным —
«на связи» горит у всех, — и поломку потом негде искать. Молча пропадающие
сообщения хуже явной ошибки, поэтому включать это можно только осознанно.

Состояние недостижимо и на сервере с настройками по умолчанию: `MAX_ROOM_PEERS = 8`,
а star включается только **сверх** порога в 8 человек.

### Что ещё предстоит сделать для relay

- Конверт пересылки: заголовок с адресатом в открытом виде + запечатанное тело,
  на ctrl- и file-канале. Содержимое остаётся невидимым для relay, адресат — нет.
- Пересылка Yjs-обновлений, awareness, ctrl-сообщений и чанков файлов.
- Backpressure через relay: место в очереди листа должно отражать очередь
  канала relay → адресат, а не собственную. Без этого отправитель зальёт файл
  в буфер relay.
- Ограничение нагрузки relay на стороне relay: при перегреве объявлять
  перегрузку (сам механизм объявления уже есть, авто-детект — нет).

### Что видит relay

Relay — обычный участник комнаты. Он видит **метаданные**: кто в комнате, кто
кому и когда отправляет, сколько байт. Содержимое он не видит: тело запечатано
ключом, который выводится из ECDH agree-ключей **конкретной пары**
отправителя и получателя (`deriveMemberKeys` в `@rd/crypto`). Agree-ключи
публичны, поэтому общий секрет считается без живого соединения, но требует
чужого приватного ключа, а он есть только у владельца.

Проверяется отдельным тестом: ключ, собранный «как наивная схема» — только из
парольной фразы и публичных identity-ключей пары, — не открывает кадр. Без
ECDH relay расшифровал бы всё тем же кодом, что и отправитель, и пересылка была
бы прозрачной, выглядя как E2EE.

## Передача файлов и backpressure

Отправитель шлёт чанки по 16 КБ в отдельном канале `rd-file`, не дожидаясь
опустошения буфера после каждого чанка. Два ограничения работают одновременно:

- **Место в канале.** Перед отправкой проверяется `bufferedAmount`; выше
  256 КБ новый кадр не берётся. Порог события `bufferedamountlow` — 128 КБ, то
  есть строго ниже границы: событие по спецификации WebRTC срабатывает только
  при переходе *строго выше порога* в «не выше порога», поэтому порог обязан
  находиться ниже отметки, до которой реально доходит очередь. Плюс опрос
  буфера каждые 10 мс и таймаут 20 с — ждать вечно нельзя.
- **Окно по подтверждениям.** Получатель шлёт кумулятивный `file-ack` после
  записи каждого чанка. Пока неподтверждённых данных больше 256 КБ, отправитель
  ждёт следующего ACK (таймаут 20 с). Локальный буфер SCTP освобождается, когда
  байты ушли в сокет получателя, а не когда он их записал, поэтому окно по ACK
  дополнительно держит узкое место получателя.

Подробный журнал (номер чанка, `bufferedAmount`, паузы, таймауты) идёт в
`onTrace` и в браузере пишется в консоль под префиксом `[rd/передача]` — по нему
видно, на каком чанке передача встала.

Проверено тестами `packages/p2p/tests/backpressure.test.ts` на mock-канале с
настоящей очередью: рост `bufferedAmount`, событие по спеке, замедленный
приёмник и сеть, переставшая забирать данные без закрытия канала.

Выход из комнаты во время передачи не считается ошибкой: цикл отправки замечает
остановку до отправки очередного кадра, поэтому пользователь не видит
«передача прервана: канал закрыт» в момент, когда он сам нажал «Выйти». На это
есть отдельный тест.

Докачка работает и после того, как файл уже отправлен целиком: задача живёт до
подтверждения от получателя, поэтому «пришли ещё раз с N» не остаётся без
ответа. На это тоже есть отдельный тест.

### Передача книги — только по запросу

Кнопка называлась «Передать участникам», а значила «всем, кто сейчас на связи»:
`share()` слал `file-offer` каждому готовому пиру, и книга уезжала молча —
согласие получателя не требовалось, отказаться было нечем. У другого человека в
каталоге висела надпись «получите от участника» без кнопки.

Теперь цепочка такая:

1. У кого файла нет — кнопка **«Запросить книгу»** (и «Отменить запрос»).
2. У владельца появляется метка **«Борис хочет скачать»** с кнопками
   **«передать»** и **«отказать»** для каждого просившего.
3. `share()` получает явный список пиров и отправляет файл **только им**.
   Если запросивших нет, `shareBook` честно отказывает, а не делает вид, что
   файл куда-то ушёл.

Запросы живут только в памяти и только между пирами: в CRDT-документ они не
попадают намеренно — это не содержимое комнаты, а личное намерение, которое
должно исчезнуть вместе с вкладкой.

Сообщение `book-decline` означает два разных вещи — отказ владельца и отзыв
запроса самим просившим. Различаются они по тому, есть ли у нас **входящий**
запрос от этого пира; проверка входящих идёт первой, иначе отзыв запроса не
убирал бы метку у владельца, и кнопка «передать» продолжала бы звать того, кто
уже передумал.

### «Кто где слушает» — только по одной записи

Список присутствия брал у соседа поле времени, не глядя, **какую** книгу тот
слушает. Я слушаю первую запись, сосед — вторую, и в моём плеере у него
отмечалась его секунда: цифра выглядела правдоподобно и относилась к другой
книге.

В `PeerReading` добавлено `audioBookId`; в списке «кто слушает эту» остаются
только те, кто слушает открытую запись, а остальные перечислены отдельно — с
названием своей. Поле из awareness при этом сверяется с нашим каталогом: чужой
`bookId` в списке не значит ничего.

## Аудиокниги и синхронизация позиции

Плеер — нативный `<audio>` с нашей разметкой поверх. Howler.js сознательно не
использован: он не понимает M4B (а это mp4-контейнер), декодирует файл целиком
через `decodeAudioData` — то есть аудиокнига на 800 МБ окажется в RAM — и пишет в
глобальный синглтон, из-за чего две книги в разных вкладках мешают друг другу.
`<audio>` играет потоком и берёт mp3, m4a, m4b и AAC без обвязки.

Что умеет: play/pause, перемотка, громкость, шкала с текущим временем и
длительностью, список глав M4B, комментарии по таймкоду с перемоткой по клику,
присутствие участников с их позициями и перемоткой к любому из них.

**Мягкая синхронизация.** Тумблер в интерфейсе, по умолчанию выключен. Наивный
вариант «разошлись — seek к соседу» в комнате не работает: два участника
получают встречные коррекции, и позиция прыгает. Отсюда четыре правила:

1. Ведущий выбирается по **минимальному `peerId`** среди слушающих ту же книгу и
   играющих, причём мы в этом списке тоже участвуем. Иначе каждый считал бы
   лидером другого и они бы тянули друг друга навстречу.
2. Коррекция — только при расхождении больше **5 секунд**: меньшее даёт сама сеть.
3. Не чаще раза в **5 секунд**, плюс пауза 10 секунд после коррекции.
4. Чужая позиция учитывает задержку сети, но не больше **3 секунд** — при
   устаревшем `at` (пир ушёл в фон) прибавление «прошедшего времени» утащило бы
   всех на минуты вперёд.

Троттлинг публикаций (1,5 с) не применяется к перемотке и к паузе: это
осознанные действия человека, о которых соседям нужно узнать сразу.

Комментарии по таймкоду идут по общей шкале прогресса вместе с текстовыми, так
что спойлер в конце записи скрывается до тех пор, пока слушатель туда не
дошёл, — и открывается, как только дошёл.

Покрыто тестами: `packages/web/tests/audio-core.test.ts` (25), `audio-player.test.ts`
(26), `audio-sync.test.ts` (10) — синхронизация проверяется на двух настоящих
документах Yjs с реальным awareness.

## Что нашли сквозные UI-тесты

Два бага, которые юнит-тестами и проверкой вручную поймать было нельзя. Оба
относились к сквозным сценариям и оба молчали: приложение не падало — оно
показывало неверное состояние.

1. **Позиция аудио никогда не уходила соседям во время воспроизведения.**
   Эффект, публикующий позицию, зависел от `snap.currentSec` — значения, которое
   меняется несколько раз в секунду. React пересоздавал эффект на каждом кадре и
   гасил недожданный `setInterval(1500)`, поэтому таймер не успевал сработать ни
   разу. На паузе снимок не меняется, и публикация работала — из-за чего
   синхронизация «работала» в покое и молчала в живом воспроизведении. Замер:
   0 вызовов при playing, 4 вызова за 6 секунд на паузе. Теперь в тике читается
   живой геттер `player.positionSec`, и снимок из зависимостей убран.

2. **Файл книги доходил, но читалка об этом не узнавала.** Запись в каталоге
   приходит по CRDT сразу, а файл — отдельной передачей через несколько секунд.
   Читалка пыталась открыть книгу один раз и, получив отказ, навсегда показывала
   «Файл книги ещё не получен. Попросите участника передать его» — даже когда
   файл уже лежал на диске. Пришлось нажимать на книгу в списке второй раз. В
   плеере было то же самое плюс защита `openedRef`, запрещавшая повтор. Теперь
   эффект переоткрытия зависит от признака «файл этой книги на диске».

Общее у обоих: правило сформулировано верно, а зависимость эффекта не отражала
условие, от которого это правило зависит.

## Известные ограничения

- **Полная mesh-топология**: каждый связан с каждым, без ретрансляции. При
  лимите в 8 участников это 28 соединений. Для больших комнат нужен узел-релей,
  и тогда он увидит чужой трафик — это осознанный компромисс приватности.
- **Нет TURN по умолчанию.** Между двумя симметричными NAT соединение не
  установится. TURN видит шифротекст и метаданные, поэтому его подключение —
  явное решение оператора (`ICE_SERVERS`). Взамен приложение обходится STUN,
  который даёт достаточно кандидатов для большинства домашних сетей; см. раздел
  «STUN и TURN».
- **Передача по запросу проверена на двух участниках.** Mock-сеть WebRTC держит
  ровно две стороны соединения, поэтому сценарий «Ваня и Дима просят, файл уходит
  только Диме» в автоматических тестах не собирается. Круг передачи покрыт по
  частям: отказ при отсутствии запросов, отказ ушедшему просившему, передача
  ровно запрошенному. Список просивших из нескольких человек на трёхживой
  комнате вживую не проверен.
- **Ограничение 8 участников** задано конфигом, но клиентская сторона
  переговоров не масштабируется линейно; проверялось на двух-трёх пирах.
- **P2P проверен настоящими двумя браузерами.** Раньше здесь стояло утверждение,
  что WebRTC в среде разработки физически не работает и отдаёт ноль
  ICE-кандидатов. **Это было неверно**: проверка была сделана для пустого
  `RTCPeerConnection` с STUN, и в выводе не хватало одного шага — answer на
  offer. Собранные e2e-тесты запускают два настоящих контекста Chromium через
  signaling, ICE сходится, DataChannel открывается, по нему едут книги,
  комментарии и синхронизация позиций. Проверка окружения осталась отдельным
  скриптом `packages/e2e/webrtc-smoke.mjs`.
- **Сквозные тесты гоняют две вкладки на одной машине.** Это проверяет протокол,
  шифрование и интерфейс, но не сеть: NAT, симметричные адреса и TURN не
  воспроизводятся. Протокол дополнительно проверен тестами на in-memory
  реализации WebRTC (`packages/p2p/tests/mock-webrtc.ts`) и на настоящей
  `RoomSession` с настоящим Dexie (`packages/web/tests/session-transfer.test.ts`).
- **STUN по умолчанию — внешний.** Клиент обращается к публичному STUN Google,
  если signaling не дал свой список. Это видно оператору STUN: ваш внешний адрес
  и сам факт соединения. Содержимого комнаты и ключей он не получает — трафик
  идёт по E2EE. Положите `VITE_ICE_FALLBACK=` пустым, чтобы не обращаться никуда;
  приложение продолжит работать внутри одной сети.
- **CORS signaling-сервера по умолчанию открыт для любого источника.** Ограничивать
  нечего: WebSocket-эндпоинт всё равно доступен любому сайту, а `/config` без
  CORS недоступен клиенту с другого домена. Задайте `CORS_ORIGIN`, если не хотите,
  чтобы ваш сервер служил чужим страницам.
- **Star-топология выбрана, но трафик через relay не пересылается.** Выбор relay,
  перевыборы, ручной выбор и построение соединений работают и покрыты тестами;
  самой пересылки нет. Поэтому она выключена по умолчанию
  (`RoomMeshOptions.relay = false`), а состояние недостижимо при
  `MAX_ROOM_PEERS = 8`. Расширять лимит комнаты, не дописав пересылку, нельзя:
  участники будут видеть друг друга «на связи» и при этом не получат сообщений.
- **Список пиров шире списка соединений.** В star лист «знает» про всех
  участников комнаты, но соединён с одним. Такие пиры остаются в состоянии
  `new`, и в интерфейсе это пока выглядит как «соединяется», а не как «соединение
  не предусмотрено — идёт через relay». Отдельного состояния для этого пока нет.
  Из-за этого проверки надо писать по соединениям (`shouldConnect`), а не по
  списку пиров: попытка сравнить «список до и после» ловит не поломку, а
  закономерный рост состава комнаты.
- **NAT-топологии не воспроизведены.** Сквозные тесты гоняют две вкладки на одной
  машине: это проверяет протокол, шифрование и интерфейс, но не сеть. Проверить
  соединение между двумя разными домами можно только руками.
- **Аудиокниги** играют, но проверены без живого звука: в среде разработки нет
  аудиоустройства. Декодирование проверяется на настоящем файле в браузере
  (e2e), но сам звук на вашей машине не звучал — это стоит проверить руками.
  Логика плеера (позиция, перемотка, синхронизация, главы M4B) покрыта тестами
  на подставном элементе.
- **Главы M4B** читаются из атома `moov.udta.chpl` (формат Nero) в первом
  мегабайте файла. Другие варианты разметки глав не разбираются, и список глав
  будет пустым — книга при этом играет нормально.
- **Синхронизация позиции выключена по умолчанию.** Это осознанно: навязывание
  чужой позиции без явного согласия — худшее, что может сделать плеер в чужой
  комнате. Она работает как «мягкое следование»: коррекция только при расхождении
  больше 5 секунд, не чаще раза в 5 секунд, с выбором одного ведущего на комнату.
- **Иллюстрации в EPUB и FB2** показываются как подпись в квадратных скобках.
  Сами картинки не рисуются: в EPUB это отдельный кэш и своя система путей, в FB2 —
  Base64 внутри файла.
- **FB2 проверен на синтетических фикстурах, а не на настоящих файлах.**
  Окружение без сети, скачать книги негде. Фикстуры воспроизводят те особенности
  реальных файлов, из-за которых FB2 приходится разбирать отдельно: однобайтовые
  кодировки без BOM и без объявления, UTF-8 с BOM, враньё в объявлении, незакрытые
  `<p>`, «голый» ампersand, `<binary>` с Base64, `<empty-line/>`, `<script>`,
  `<iframe>`, `onload` и `javascript:`-ссылки. Честного подтверждения, что
  разбираются книги конкретных издательств, здесь нет: первый настоящий FB2
  может потребовать правок.
- **`<empty-line/>` в FB2 схлопывается в обычный разрыв абзаца.** Отдельный блок
  для пустой строки нарушал бы инвариант рендерера (см. `isBlockVisible` в
  `packages/library/src/reader.ts`): пустой блок не рисуется. В стихах такая
  разбивка на строфы поэтому теряется.
- **Сноски в FB2** попадают в текст как обычные абзацы, а `<a l:href="#note1">`
  ведёт в никуда: переходы по сноскам не сделаны.
- **Синхронизация запускается только при активном воспроизведении.** Участник,
  который слушает на паузе, не становится ведущим: иначе группа замирала бы на
  паузе одного человека.
- **Перемотка при смене битники.** Позиция хранится в awareness в секундах, а не
  в долях. Если участники получили разные копии одной записи с разной
  длительностью, таймкод может разойтись на доли секунды.

## Что стоит сделать перед публичным запуском

1. Проверить FB2 на настоящих книгах: раздел «FB2» выше описывает фикстуры, а не
   реальные издания. Первая настоящая книга с неожиданной разметкой потребует
   правок.
2. Иллюстрации в EPUB и FB2 (сейчас — подпись в квадратных скобках).
3. Переходы по сноскам и внутренним ссылкам в FB2.
4. `RoomRelay` для комнат больше 8 участников, с явным предупреждением о том,
   что узел видит трафик.
5. Сборка десктопа на Tauri: слой хранения уже за интерфейсом `LibraryStore`,
   но реализация под SQLite не написана.
6. Нагрузочная проверка signaling на целевой машине (1 vCPU / 1 ГБ): тесты
   покрывают лимиты, но не тысячи одновременных соединений.

## Лицензия

MIT, файл `LICENSE` в корне. Лицензия указана единым полем `license` в
`package.json` и во всех пакетах монорепозитория — копий лицензии по папкам
пакетов нет намеренно: в монорепозитории один корень и один файл, иначе через
полгода в разных пакетах окажутся разные лицензии.

Раньше код был под AGPL-3.0-or-later. Смена на MIT — ослабление требований:
по AGPL изменённый сетевой сервис обязан открыть изменения, по MIT — нет.
Правообладатель здесь один (все коммиты одного автора), так что права на
смену лицензии целиком.

Что стоит знать перед распространением: MIT не содержит **явной передачи
патентных прав**. Для сетевого кода это иногда важно — есть классы решений,
патентные риски по которым традиционно считают значимыми (WebRTC и
смежные стеки). Если это для вас важно, Apache-2.0 даёт явную передачу
патентов и защиту от патентных претензий к вкладчикам; замена сводится к
двум файлам — `LICENSE` и полю `license` в восьми `package.json`.

Имя правообладателя в `LICENSE` оставлено плейсхолдером
`Copyright (c) 2026 <Your Name>`: замените на своё перед публикацией.
