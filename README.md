# rd — совместное чтение книг и аудиокниг в приватных комнатах

Децентрализованное P2P-приложение. Книги, комментарии и прогресс живут только на
устройствах участников; signaling-сервер помогает соединиться и не видит
содержимого комнаты.

```
┌──────────┐   WSS (SDP/ICE)   ┌──────────────┐   WSS (SDP/ICE)   ┌──────────┐
│  Аня     │ ────────────────► │  signaling   │ ◄──────────────── │  Борис   │
│ браузер  │ ◄──────────────── │  (stateless) │ ─────────────────► │ браузер  │
└────┬─────┘                    └──────────────┘                    └────┬─────┘
     │                                                                   │
     │        Data Channel: AES-GCM, заголовок кадра = AAD               │
     └─────────────────────── E2EE, напрямую ────────────────────────────┘
                                    │
                       ┌────────────┴────────────┐
                       │   Yjs: комментарии,      │
                       │   каталог, присутствие    │
                       │   файлы — чанками по 16 КБ│
                       └────────────────────────────┘
```

## Что реализовано

| Область | Состояние |
|---|---|
| Комнаты: создание, вход по id + фразе, список участников, статусы | готово |
| E2EE: PBKDF2 → ECDH P-256 + Ed25519 → HKDF → AES-GCM с окном переигрывания | готово |
| Код безопасности (защита от подмены ключей посредником) | готово |
| P2P: mesh, perfect negotiation, два канала (управление / файлы) | готово |
| CRDT: комментарии (треды, реакции), каталог книг, присутствие | готово |
| Передача файлов: чанки 16 КБ, SHA-256, скользящее окно 256 КБ, backpressure по `bufferedAmount` и по ACK, докачка с обрыва | готово |
| EPUB: разбор, оглавление (EPUB 3 и NCX), рендер без `innerHTML` | готово |
| Якоря комментариев: цитата + контекст, устойчивость к переразметке | готово |
| Спойлеры: маскирование до места комментария | готово |
| Офлайн-режим: состояние комнаты в IndexedDB | готово |
| Аудиокниги: плеер, таймкоды, комментарии по времени | модель данных и якоря есть, плеера нет |
| FB2 | не начато |

Что осознанно не входит: аккаунты, серверная модерация, любые данные на сервере,
телеметрия. Код под AGPL-3.0.

## Запуск

Нужен Node.js ≥ 20.11 (в тестах использовался 22.23) и браузер с WebRTC
(Chrome 137+, Firefox 130+, Safari 17+). WebRTC требует HTTPS или `localhost`.

```bash
npm install
cp .env.example .env          # необязательно, умолчания рабочие

npm run dev:server            # signaling на :8787
npm run dev                   # клиент на :5173
```

Продакшен-сборка:

```bash
npm run build                 # signaling (esbuild) + клиент (vite)
npm run start:server
```

Откройте приложение в двух вкладках, создайте комнату в первой, скопируйте
идентификатор во вторую, введите одну и ту же парольную фразу.

## Проверки

```bash
npm run typecheck             # tsc --noEmit по всему монорепо
npm test                      # 115 тестов
npm run test:coverage
```

Покрытие — около 88 % строк. Не покрыт `packages/web`: интерфейс проверялся
руками в браузере (вход в комнату, обнаружение участников, разбор книги,
привязка комментария), но автотестов компонентов нет. Это осознанный долг:
первый вертикальный срез делался вертикальным.

Основной тест — не юнит-тесты, а `packages/p2p/tests/mesh.test.ts`: две ноды
проходят весь путь (подключение → E2EE-рукопожатие → синхронизация Yjs →
передача файла → докачка после обрыва) на in-memory реализации WebRTC. Ошибки
на стыках слоёв — несовпадение направлений ключей, потерянный заголовок кадра,
зацикливание broadcast, гонки в обработке чанков — не видны в юнит-тестах по
отдельности, и именно их ловит этот тест.

|---|---|---|
| `@rd/protocol` | типы сообщений, валидация, бинарный фрейм | — |
| `@rd/crypto` | KDF, ECDH, подписи, AEAD-канал, код безопасности | protocol |
| `@rd/p2p` | транспорт, mesh, Yjs-провайдер, передача файлов | protocol, crypto, yjs |
| `@rd/library` | EPUB, якоря, документ комнаты, IndexedDB, рендер | protocol, p2p, dexie |
| `@rd/signaling` | сервер: реестр комнат, лимиты | protocol, fastify |
| `@rd/web` | React-клиент | все |

Пакеты поставляются исходниками: Vite и Vitest резолвят `@rd/*` через алиасы
прямо в `src`. Собирается отдельно только signaling — он исполняется на Node.

## Ключевые инженерные решения

### Почему свой signaling, а не Trystero и не y-webrtc

`y-webrtc` ходит через публичные трекеры и не шифрует полезную нагрузку: там
комната защищена только именем, а весь CRDT-трафик виден оператору трекера.
Trystero устроен так же. Для приложения, где единственная ценность — приватность,
это неприемлемо, поэтому signaling и Yjs-провайдер написаны здесь: ~200 строк
поверх `y-protocols`, протокол совместим с любым другим Yjs-клиентом.

### Откуда берётся ключ пары

В KDF входят три независимых материала:

- **парольная фраза** — её знают только участники комнаты; сервер не может
  прочитать данные;
- **ECDH P-256** — приватный ключ есть только у пира; посредник, подменивший
  публичные ключи, не сможет установить рабочий канал даже со знанием фразы
  (соединение просто не расшифруется);
- **отсортированные identity-ключи** — чтобы направление ключей не зависело от
  того, кто подключился первым.

Каналы `ctrl` и `file` разведены по разным `info`, а каждое направление — по
своей роли: четыре независимых ключа AES на пару, поэтому счётчики nonce можно
начинать с нуля в каждом направлении и никогда не повторить пару «ключ + nonce».

P-256, а не X25519: WebCrypto в Node не знает кривую `X25519`, и без неё
криптографию нельзя покрыть тестами без браузера. Формат провода хранит байты
ключей, поэтому переход — смена одной константы.

### Почему заголовок кадра передаётся открытым

Заголовок нужен AEAD как additional data, а AAD задаётся **до** шифрования —
зашифровать его нельзя. Поэтому в заголовке лежит только тип кадра и, для чанка
файла, идентификатор передачи, смещение и длина. Всё содержимое — в
зашифрованном теле. Из-за этого в крипто-пакете намеренно **нет** метода
«зашифровать JSON в заголовок»: такая возможность один раз утекла бы весь чат
комнаты в открытом виде, и тест на это есть.

### Якоря комментариев вместо CFI

Якорь — это (глава, блок, смещение) **плюс цитата с контекстом**. Он переживает
переразметку, переносы строк и другую разбивку на абзацы. Поиск идёт от
точных координат к цитате в блоке, затем в главе, затем по книге.

Инвариант, на котором всё держится: дерево блока нормализуется **на этапе
разбора**, поэтому `text(дерево) === block.text`, а смещения в DOM равны
координатам якоря. Без этого комментарии привязывались бы к произвольным местам.

### Контрольная сумма файла

`root = SHA-256( SHA-256(чанк₀) ‖ … ‖ SHA-256(чанкₙ) )`. Хеши считаются
потоково, файл не держится в памяти целиком. Хеши чанков сохраняются рядом с
данными, поэтому после обрыва связи общая сумма собирается заново, а файл не
качается с нуля.

### Никакого `innerHTML`

Содержимое EPUB недоверенное. DOM строится через `createElement`/`textContent`
из разобранного дерева с закрытым белым списком тегов; атрибуты вида `onclick`
и `style` не копируются вообще, текст книги всегда остаётся текстом. Санитайзер
не нужен, потому что нет пути для выполнения кода.

## Передача файлов и backpressure

Отправитель шлёт чанки по 16 КБ в отдельном канале `rd-file`, не дожидаясь
опустошения буфера после каждого чанка. Два ограничения работают одновременно:

- **Место в канале.** Перед отправкой проверяется `bufferedAmount`; выше
  256 КБ новый кадр не берётся. Порог события `bufferedamountlow` — 128 КБ, то
  есть строго ниже границы: событие по спецификации WebRTC срабатывает только
  при переходе *строго выше порога* в «не выше порога», поэтому порог обязан
  находиться ниже отметки, до которой реально доходит очередь. Плюс опрос
  буфера каждые 10 мс и таймаут 20 с — ждать вечно нельзя.
- **Окно по подтверждениям.** Получатель шлёт кумулятивный `file-ack` после
  записи каждого чанка. Пока неподтверждённых данных больше 256 КБ, отправитель
  ждёт следующего ACK (таймаут 20 с). Локальный буфер SCTP освобождается, когда
  байты ушли в сокет получателя, а не когда он их записал, поэтому окно по ACK
  дополнительно держит узкое место получателя.

Подробный журнал (номер чанка, `bufferedAmount`, паузы, таймауты) идёт в
`onTrace` и в браузере пишется в консоль под префиксом `[rd/передача]` — по нему
видно, на каком чанке передача встала.

Проверено тестами `packages/p2p/tests/backpressure.test.ts` на mock-канале с
настоящей очередью: рост `bufferedAmount`, событие по спеке, замедленный
приёмник и сеть, переставшая забирать данные без закрытия канала.

## Известные ограничения

- **Полная mesh-топология**: каждый связан с каждым, без ретрансляции. При
  лимите в 8 участников это 28 соединений. Для больших комнат нужен узел-релей,
  и тогда он увидит чужой трафик — это осознанный компромисс приватности.
- **Нет TURN по умолчанию.** Между двумя симметричными NAT соединение не
  установится. TURN видит шифротекст и метаданные, поэтому его подключение —
  явное решение оператора (`ICE_SERVERS`).
- **Ограничение 8 участников** задано конфигом, но клиентская сторона
  переговоров не масштабируется линейно; проверялось на двух-трёх пирах.
- **P2P между двумя вкладками в этой среде не проверено.** Окружение, в котором
  велась разработка, отдаёт ноль ICE-кандидатов даже для пустого
  `RTCPeerConnection` с STUN, то есть WebRTC там физически не работает.
  Протокол проверен тестами на полной in-memory реализации WebRTC
  (`packages/p2p/tests/mock-webrtc.ts`): рукопожатие, AEAD, синхронизация Yjs,
  передача файла и докачка после обрыва.
- **Аудиокниги** не реализованы: есть формат данных, якоря по таймкоду и
  правила спойлеров, нет плеера.
- **Иллюстрации в EPUB** показываются как подпись в квадратных скобках.
- **FB2** не начат; точка расширения — `packages/library/src/epub.ts`, рядом
  лежит структура `EpubBlock`, общая для обоих форматов.

## Что стоит сделать перед публичным запуском

1. Аудиоплеер с таймкодами и синхронизацией позиции между участниками.
2. FB2-парсер (структура общая с EPUB).
3. Синхронизация позиции аудио между пирами с настраиваемым «мягким» режимом.
4. `RoomRelay` для комнат больше 8 участников, с явным предупреждением о том,
   что узел видит трафик.
5. Сборка десктопа на Tauri: слой хранения уже за интерфейсом `LibraryStore`,
   но реализация под SQLite не написана.
6. Нагрузочная проверка signaling на целевой машине (1 vCPU / 1 ГБ): тесты
   покрывают лимиты, но не тысячи одновременных соединений.
